问题 A：「获取模型」字段名不匹配（真 bug） ​

修法：改后端读 api_key（选项 b）。 理由：

  1. api_key 在本项目里已经是「上游 provider key」的专有名——ir/credential.ts 的 CredentialType、credentials/resolver.ts 的存储类型、gateway-core/pipeline/types.ts 的入站字段、auth/data-plane.ts 的 material.api_key 都叫这个；
  2. 裸 key 与虚拟 key 域撞名——SettingDto 的标识符当年就叫 key，把前端 secretTripwire 整页误拦过，后来改名 id（webui/admin/src/api/types.ts 有注释）；
  3. 前端 tripwire 的字段名辅助判据（SECRETISH_NAME_RE）认 api_key 不认裸 key。

顺带把前端镜像补齐成契约原样（都是同一族的漂移）：

  • 补 dialect——后端按它推发现端点路径（Anthropic → /v1/models），原先漏发， 非 DeepSeek 的上游会打到错误的路径；
  • 补 provider_id——已存模式原先两个都不发，编辑渠道点「获取模型」必然 400；
  • 删 preset_id / access_path_id——后端一个都不读。

同一族还修了一个判据错误 ​

上游侧失败一律回 502（admin/routes.ts 的 providerModelsHttpStatus：401 会被当成 会话过期跳登录页，所以不用 401 表示 key 无效），契约明写「具体哪一类由 error.code 说」。 但前端分类器只认状态码 → 「key 无效」显示成「上游故障 · 重试」，让人去重试一把明明白白 无效的 key。现在先认 error.code 再认状态码 （webui/admin/src/api/provider-models.ts 的 CODE_TO_FAILURE）。 没进表的四个（invalid_json / invalid_shape / credential_missing / invalid_request） 仍走兜底，后端那句话会作为详情附在文案后——界面显示的是「获取模型失败（该渠道还没有可用凭据）」， 没有把没发生的事说成发生了。

问题 B：可编辑字段看不出可编辑 ​

根因不在面板代码，在令牌：这套主题下 Semi 输入框的边框是透明的 （--semi-color-border 只有 10% 不透明度），底是 5% 的灰。实测（getComputedStyle）：

措施：

  • theme.css §9.2b：全站表单控件补表面色底 + 实线边框 + hover 转强调色 + focus 柔光；
  • panels.css：接入表三个可编辑列（协议 / base_url / access_path）挂 .ag-panel-cell， 同口径但选择器写到两级，盖过 Semi 自己那级；
  • 列头带「可编辑」悬停提示；
  • 窄格长 URL：展开编辑按钮 + 双击展开，展开后是全宽编辑器（实测输入框宽 445px vs 格内 179px）；
  • 「能力状态」区逐个确认过：0 个 input、0 个可点按钮（只读三态，interactive: false 写死在类型里）——那一区本来就没有可编辑字段，不画假开关。

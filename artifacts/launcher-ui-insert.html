launcher-ui 插入点 · Launcher UI 架构与选址 ​

结论先行
推荐 **方案 A：`src/main/ui/kit/`**（导入路径 `@ui/kit`）。 理由一句话：它是唯一「框架内建、toggle 关不掉、零新增构建配置、三端（Electron / 浏览器 / 安卓 WebView）共用同一份 bundle」的位置。文末有 5 个需要你拍板的问题。

1. 现状：UI 资产实际分布 ​

渲染端只有一个 Vue 应用，electron.vite.config.ts 把 src/main/ui 设为 renderer root 并注册别名，所以「框架 UI」和「能力 UI」在同一个构建图里，靠目录分层：

被跨能力复用的只有 5 个：LoadingBar / AbilityIcon / AutoSaveHint / SettingsCategoryView / PrivacyText。 其余 150 处 import 几乎全是 translate / useI18n——大家共享的是语言函数，不是布局与组件。

也就是说：规范是文档，不是代码。新页面「几分钟写出不出错的 UI」缺的正是把 DESIGN.md 的底线编译成组件默认值的那一层。

3. 四个候选插入点 ​

推荐
A. src/main/ui/kit/
框架内新子目录，barrel 导出，@ui/kit 导入。toggle 关不掉、零构建配置、三端共用。
次优
B. src/main/ui/components/ 并列
直接塞进现有 components/。省一个目录，但外壳 chrome 与通用积木混在一起，语义会继续腐化。
否决
C. 伪 ability src/abilities/ui-kit/
能白拿能力体系的翻译与设置注入，但会被 toggle.json 和 --only 精简掉，还要写空的 commands.ts。用户已明确不要 ability。
过重
D. 独立 npm 包 packages/launcher-ui/
要改 renderer root / alias / pnpm workspace / headless 构建脚本，且组件要跨包消费 --v-theme-* 与框架 i18n。只有要给 Launcher 之外用时才值得。

为什么是 A ​

  1. 框架内建 → 精简构建免疫。toggle.json 的 glob 排除只作用于 src/abilities/*；放 src/main/ui/ 里，你的 slim 部署（{"*":false} 白名单）照样带着整套 UI 库，随时能写新页面。
  2. 零新增构建配置。@ui 已 alias 到 src/main/ui，renderer root 也是它；scripts/build-headless.mjs 直接复用 electron.vite.config.ts；安卓 App 的 WebView 加载同一份产物。三个消费方都不用改一行。
  3. 自动共享 chunk。多个能力动态 import 同一个 kit 模块时 Vite 会抽成公共 chunk，不会复制进每个 ability 的包。
  4. 规范可执行。密度、chip 内边距、空状态观感、页壳 min-height: calc(100vh - 96px)、手机 px-3 全部变成组件默认值——用就对，而不是「记得看文档」。
  5. 可测试。纯渲染端，能挂 vitest + 已有的 vue-tsc / 模板编译检查。

D 不是被否掉，而是 A 的超集：先按 A 落地，真到要给外部用时，把 kit/ 连目录挪进 packages/，导入路径不变。

4. 建议的目录与导入形态 ​

src/main/ui/kit/
  index.ts               # 唯一 barrel：显式导出（不用 glob → 名字稳定、可 tree-shake）
  kit.css                # 只放积木级样式；主题变量仍归 color_schemes
  components/
    layout/    KitPage  KitSection  KitGrid  KitToolbar
    data/      KitList  KitKeyValue  KitTree  KitTable
    form/      KitField  KitSwitch  KitFormDialog
    feedback/  KitEmpty  KitChip  KitProgressRow
    nav/       KitTabs  KitNavStack(包 useNavStack)  KitFab
  composables/
    useAdaptive.ts       # 桌面/手机统一断点（包 viewport.ts + Vuetify useDisplay）
    useAsyncState.ts     # loading / error / empty 三态，配 LoadingBar
  docs/launcher-ui.md    # 每个积木「什么时候用 / 不要用什么」

导入形态与现状一致，能力里就这样写：

ts
import { KitPage, KitSection, KitToolbar, KitEmpty } from '@ui/kit'

第一批积木（直接消灭上表的重复） ​

积木固化的 DESIGN.md 规则
KitPage能力页外壳：flex 列 + min-height: calc(100vh - 96px) + 手机容器 px-3
KitToolbar图标组 size="small" + ga-1，文字组默认密度 + ga-2，flex-wrap 兜底
KitChippadding-block: 4px + min-height: 24px，label 不贴边
KitEmpty统一 v-empty-state 观感（DESIGN.md §7），禁止各页手写大图标
KitSection卡片区块：标题 + 操作插槽 + 内容，统一 py-3
KitTree吃掉 3 份 JSON 树重复
KitFormDialog移动端自动 bottom-sheet、桌面居中
useAsyncState三态 + command(..., { silent: true }) 语义（刚做好的 DI 静默通道）

兼容与安全底线（写进 kit 的 README） ​

  • 组件不许 import electron；宿主能力（窗口 / 文件 / 剪贴板）一律 window.cockpit.hasCap(...) 降级，保证无头网页与安卓 WebView 可用。
  • 文案走框架翻译 + kit.* 命名空间，不占 ability 的 translations/。
  • 隐私标签（v-privacy / v-agent-forbidden）保持可用，kit 不能成为 AI 视线的盲区。
  • 每个积木过 pnpm typecheck + 一条 vitest props 契约测试。

5. 落地路线 ​

  1. 1
    立骨架
    kit/ + barrel + kit.css + docs 占位，半天；先只放 KitPage / KitSection / KitEmpty 三个，跑通构建与 headless。
  2. 2
    补第一批 8 个积木
    配 vitest；同时做一个 gallery 展示页（见 Q2）当活文档。
  3. 3
    重写两个样板能力页
    用 mirror / autostart 这类最小页面做参考实现，验证「几分钟一个页面」的说法。
  4. 4
    约束新页面 + 渐进迁移
    新 UI 必须用 kit；旧页面按触碰即迁移，不做大爆炸重写。

6. 需要你抉择 ​

Q1 命名与路径
src/main/ui/kit/（@ui/kit）还是 src/main/ui/launcher-ui/（@ui/launcher-ui）？倾向后者更贴合你起的名字，导入更长一点。
Q2 展示页
要不要一个 kit gallery？建议做成 settings 里的一个分类或 dev-only 路由，不进精简构建。
Q3 第一批范围
上面 8 个积木，还是砍到 5 个（Page / Section / Toolbar / Empty / Chip）先跑起来？
Q4 旧页面
只约束新页面，还是授权渐进迁移？（迁移会碰业务代码，建议只做样板 2 个）
Q5 未来抽包
是否现在就按「可抽成 npm 包」的边界写（组件只依赖 vuetify + kit 内部，不 import 框架私有模块）？成本极低，建议是。
这一页本身就是参考实现的样式
所有布局走组件、表格走 Markdown、决策点集中在一处——launcher-ui 的文档页也建议照这个形态组织：每个积木一节「什么时候用 / 不要用什么」。

网络 AI Workflow 架构 ​

AI 服务跑在组织私有云的一台虚拟机里，笔记本走 NetBird 覆盖网直连；手机不想占用 VPN 槽位，于是把浏览器入口暴露到公网：Cloudflare 托管 DNS → 云上入口机 → NetBird → 内网 VM。认证全部收敛到内网统一门户，公网侧只做接入和转发。

三层网络 ​

层角色机制
本地层私有云虚拟机网段，DHCP 由私有云侧下发VM 不装覆盖网客户端；CGNAT 段流量经路由策略从网关进覆盖网
覆盖网层组织自托管 NetBird，私有网段，数十个 peer网关 peer 宣告 LAN 网段；入口机侧独立路由表 + fwmark
公网层云上入口机，Cloudflare 灰云 DNS只放行部分端口；认证不在此层做决策

公网入口 ​

入口认证回源目标
DSH 入口mTLS + 门户 /checkDSH 密码门 → DSH web
opencode 入口mTLS + 门户 /checkopencode（入口代填 Basic）
noVNC 入口mTLS + 门户 /check本机 websockify → 内网 x11vnc
桌面直连入口mTLS（永久保留）+ 上游自有密钥桌面工作站 opencode
统一门户入口入口机不认证纯 TCP 转发 → 内网统一门户（TLS 端到端）
运维入口SSH 密钥运维
  • 前三个 mTLS 入口未认证时会被 forward_auth 拦下；统一门户入口由门户自己 302；桌面直连入口由上游 Basic 密钥拦截。
  • 标准 HTTP/S 端口未开放；未备案域名的 HTTP 请求会被云厂商拦截页吃掉，必须显式 https://。
  • 入口机的根 CA 私钥位置是已知风险点（加密块内详述）。

请求路径 ​

  1. 1
    手机发起 HTTPS
    公网域名经 Cloudflare 解析到入口机
  2. 2
    入口机 TLS 前置
    mTLS 入口要求客户端证书
  3. 3
    认证回调内网
    forward_auth 调内网门户 /check，同时认 Authelia 与 OAuth 会话
  4. 4
    通过后回源
    转发到 DSH / opencode / noVNC，内容才可见

认证体系 ​

  • 统一门户 + Authelia：密码 + TOTP，会话 24h 过期 / 12h 空闲。
  • GitHub OAuth 由门户自实现，按不可变数字 ID 绑定，不依赖用户名。
  • fail-closed：认证服务不可用时返回 502，绝不放行。
  • 公网只放行登录必需的最小 API 路径；注册/管理接口无入口。
  • 支持按用户名的临时封禁；退出写撤销表，已复制的 Cookie 立即失效。

AI VM 服务 ​

服务作用
统一门户登录页 + /check + 服务状态
Authelia认证后端，仅 loopback
DSH 密码门托管 DSH web，遥测关闭，出网走本地代理
opencodev2 server

headless 桌面Xvfb + x11vnc + xrdp，供 AI 截图/操作 GUI
透明代理TUN + HTTP 代理，fake-IP DNS

工作流机制 ​

  • 出网：公网域名被本地 fake-IP 解析成保留段，web_fetch 等工具必须走本地 HTTP 代理（systemd drop-in 注入）。
  • 入网：AI 产出全部挂在认证门后；手机浏览器直接访问公网入口。
  • 集群：kubectl 指向覆盖网内的开发集群 API。
  • 通知：任务完成 → 通知守护 → 即时通讯。
  • 桌面：辅助脚本操作 headless 桌面，截图 + GUI 自动化。

已知问题 ​

  • 入口机持有根 CA 私钥：整改方向是把私钥搬回内网，不是删掉 mTLS。
  • 桌面直连入口是认证路径的有意例外，使用上游自有密钥；mTLS 永久保留，即使上游密钥调整也不撤销。
  • 认证链是单点：内网断网则公网入口整体不可用（fail-closed，符合预期但无高可用）。
  • AI VM 与桌面工作站同名，脚本与文档需用别名区分。
  • OAuth client secret 建议定期轮换。
